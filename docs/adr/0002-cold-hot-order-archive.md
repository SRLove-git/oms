# ADR-0002：历史订单冷热分离（归档）方案

- 状态：已接受（2026-08-09）
- 关联需求：项目要求 F3（订单全生命周期）、SCHEDULE.md WBS-3.3

## 背景

订单表（`order`）随业务增长无限膨胀，将拖慢热数据查询、索引维护与备份恢复；项目要求阶段三明确要求做历史订单冷热分离。

## 决策

1. **归档目标表**：在 order-service 数据库新增 `order_archive`、`order_item_archive`、`order_log_archive`、`order_payment_archive` 四张与热表同构的归档表，额外记录 `archived_at`。
2. **归档条件**：终态订单（已完成 / 已取消，status in 6,7）且 `updated_at` 早于阈值（默认 180 天，`oms.order.archive-days` 可配）后进入归档。
3. **归档方式**：定时任务（`OrderArchiveScheduler`，fixedDelay 默认 1 小时，支持手动触发 `POST /api/v1/orders/archive/run`）按批（默认 200 单/批）在单事务内完成：先复制到归档表，再物理删除热表数据（含明细/日志/支付单），保证归档原子性。
4. **查询口径**：
   - 订单详情先查热表，未命中回退归档表（`GET /api/v1/orders/{orderNo}` 兼容历史单）。
   - 历史单列表提供 `GET /api/v1/orders/archived`。
   - 报表统计使用热表与归档表 `UNION ALL` 聚合，保证长周期报表口径不因归档而变化。
5. **与软删除约束的关系**：项目规范要求核心表禁止物理删除；归档是本约束的显式例外——数据并未丢失，而是转移到归档表并保证可读、可审计。归档行为与阈值配置均记录在运维手册中。

## 后果

- 热表规模可控，订单分页与超时扫描等热路径性能稳定。
- 归档表随业务增长同样需要容量规划；建议在阶段 5 前为归档表配置独立的存储或定期备份。
- 报表 UNION 会扫描热+冷两张表，已通过 `paid_at`/`status` 复合索引与 Redis 缓存（5 分钟 TTL）控制成本。
